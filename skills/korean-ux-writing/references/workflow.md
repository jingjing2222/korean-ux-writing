# 퍼널을 읽고 문구를 고치는 방법

영어 원문 없이 한국어로 작성된 제품을 기본 대상으로 삼는다. 번역 경로를 추적하거나 한국어 뒤에 있을 법한 영문을 복원하는 작업이 아니다.

이 문서는 사용자의 작업 요구를 실행하는 절차다. 문장 품질 기준은 `rules.json`과 외부 증적에서 가져온다.

## 사용자에게 전달된 맥락부터 확인한다

시작할 때 [사용자 관점 점검](user-perspective.md)을 읽는다. 제품이 어떻게 설계되었는지와 사용자가 무엇을 알고 하려는지는 별개다. 가능한 경우 사용자 화면만으로 과업을 순서대로 따라간 기록을 먼저 남기고, 전체 제품의 동작은 이후 사실 확인에 사용한다. 내부 설명을 이미 읽었다면 독립 검토의 한계를 밝힌다.

사용자가 이전 단계에서 필요한 맥락을 전달받지 못했다면 현재 문구의 길이나 말투 문제가 아니라 흐름 문제로 다룬다. 필요한 안내를 처음 제공해야 하는 단계와 이유를 찾아 개선안을 남긴다. 현재 문구에 설명을 덧붙이는 것으로 이 문제를 해결했다고 하지 않는다.

## 범위와 퍼널

먼저 앱의 진입점, 라우트 설정, 화면 목록, 번역 리소스와 공유 UI를 찾는다. 기존 테스트·스토리·제품 사양은 누락된 상태를 찾는 보조 자료다. 변경된 파일만 읽는 것으로 퍼널을 파악했다고 판단하지 않는다.

퍼널은 사용자의 목적에 따라 정한다. 예를 들어 구독 변경에는 요금제 선택뿐 아니라 현재 이용 조건, 변경 확인, 결제 요청, 접수·완료, 실패·취소, 변경 후 안내가 포함될 수 있다. 실제 코드에 없는 단계를 이 예시에서 복제하지 않는다.

퍼널마다 다음 사실을 기록한다.

| 확인할 맥락 | 읽을 자료와 질문 |
|---|---|
| 진입 | 어디에서 들어오는가? 딥링크나 재방문으로 중간 진입이 가능한가? |
| 앞 단계 | 이 진입 경로에서 실제로 제공한 약속·가격·조건·입력은 무엇인가? 필요한 순간에 다시 찾을 수 있는가? 노출 사실을 이해·기억의 증거로 삼지 않았는가? |
| 현재 단계 | 무엇을 결정하고 어떤 데이터를 다루는가? 버튼은 무엇을 실제로 실행하는가? |
| 분기 | 로그인·권한·검증·기능 플래그·응답 값에 따라 무엇이 달라지는가? |
| 뒤 단계 | 버튼 직후와 최종 결과는 각각 무엇인가? 추가 확인이나 처리가 남아 있는가? |
| 복구와 종료 | 뒤로 가기·취소·재시도 시 입력과 상태는 어떻게 되는가? 되돌릴 수 있는가? |
| 공유 사용처 | 같은 컴포넌트·번역 키가 다른 퍼널에서도 같은 의미로 쓰이는가? |

UI 코드에서 핸들러와 상태 업데이트, 호출하는 서비스·API 처리까지 따라간다. 서버의 실제 결과를 알 수 없으면 프론트엔드가 보장하는 범위를 넘어서 말하지 않는다. 라우트 한 페이지가 상태 여러 개를 담을 수 있고, 한 퍼널이 여러 파일·페이지를 가로지를 수 있다.

파일을 읽었다는 기록에는 경로만 적지 않는다. 확인한 분기·행동·조건과 코드 위치를 적는다. 전체 퍼널의 경계를 코드로 설명할 수 있을 때까지 관련 호출부를 조사한다. 조사하지 못한 경로는 `unresolved`로 남긴다.

상태는 문구의 의미·노출·행동·결과가 달라지는 지점에서 나눈다. 같은 DOM 위치라도 저장 전과 저장 후에 안내의 의미가 달라지면 각각 연결한다. 의미와 동작이 같은 값의 조합은 함께 검토할 수 있지만, 묶은 조건과 같다고 판단한 근거를 남긴다. 모든 변수 조합을 기계적으로 늘리거나, 실제 차이를 합쳐 누락하지 않는다.

## 수집

코드의 문자열 리터럴만 수집하지 않는다. 렌더링되는 사용자 문구를 아래 경로에서 대조한다.

- 화면·공용 컴포넌트의 텍스트 노드와 props, 명령형 토스트·대화창 호출.
- 번역 리소스와 번역 함수 호출부, 기본값·대체 언어·키 누락 처리.
- 검증 라이브러리의 메시지, 에러 코드 매핑, 서버에서 그대로 전달되는 문구.
- 접근성 이름·설명·대체 텍스트·상태 안내, 문서 제목.
- 문자열 보간·복수형·ICU select/plural·값에 따라 달라지는 조사.
- 권한·기능 플래그·인증·네트워크·빈 데이터 등 조건별 화면.
- 이미지·SVG·캔버스에 들어간 제품 문구. 읽기나 수정이 불가능하면 그 한계를 기록한다.

정적 검색, 구문·호출부 확인, 라우트·상태 목록, 실행 화면을 서로 대조한다. 한 방법의 결과 수를 전체 문구의 분모로 선언하지 않는다. 지원하지 않는 파일 형식, 접근 불가능한 CMS·서버 리소스, 실행하지 못한 상태를 명시한다.

## 먼저 안내 의도를 재구성한다

현재 문구가 자연스러운지 평가하기 전에 사용자의 과업과 현재까지 제공된 정보를 `UX-*` 근거로 검토한다. 코드·사양은 실제 결과와 조건을 확인하는 데만 쓴다. 현재 표현이나 리소스 키를 그대로 풀어 쓰거나, 구현된 기능을 곧 사용자가 원하는 일로 간주하면 판단이 내부 설계에 끌릴 수 있다.

[독자 이해 점검](reader-language.md)으로 이 문구를 읽는 사람, 그 사람이 알고 싶은 내용, 현재 문구로 알 수 있는 답을 대조한다. 내부 절차나 분류 이름을 반복하는 답으로 대신하지 않는다. 유지하는 문구도 해당 위치의 구체적인 근거를 남긴다.

1. **사실:** 실제 기능·상태·전이와 확인 위치.
2. **UX 요구:** 근거가 있는 사용자 과업 또는 명시한 과업 가설, 그 경로에서 실제로 받은 안내, 지금 알아야 하거나 결정할 것. `meaning_contexts`에는 실제 결과도 기록하되, `user-perspective.json`의 행동 전 예상과 분리한다.
3. **보존할 의미:** 대상·수치·단위·조건·시점·부정·예외·행위 주체·확정성.

코드에서 `updatePreference(id, value)`를 찾은 것만으로 사용자의 목적을 확인했다고 하지 않는다. 실제 사용자 조사가 없으면 검토용 과업 가설이라고 밝힌다. 그 가설로 과업을 따라가며 필요한 맥락이 사용자에게 제공되는지 먼저 확인하고, 제품의 실제 동작과 대조한다. 내부 명명·설계 의도와 맞는다는 이유로 사용자 이해에 적합하다고 하지 않는다.

같은 화면에서 문구들이 같은 과업·조건·결과를 공유하면 의미 맥락 하나를 함께 참조한다. 조건이나 사용처에 따라 뜻이 달라지면 나눈다. 같은 소스 키도 뜻이 다르면 **진단 전 원문 대장에서 별도 ID**로 구분하고 원래 키와 모든 위치를 보존한다. 이 단계에서는 소스를 고치지 않는다.

기존 안내의 주장이 실제 동작과 다르면 원래 주장과 확인한 사실을 대조한다. 다음 확인 화면으로 이동하는 버튼을 처리 완료로 설명하거나 접수를 완료로 알리는 문제는 어미를 고쳐 해결할 수 없다. 아직 확인하지 못한 동작·조건·결과를 채워 넣지 않는다.

## 현재 한국어가 그 뜻에 맞는지 진단한다

`translationese.json`을 읽고 대장의 모든 사용처를 검토한다. 먼저 LT-05로 확인한 안내 의도와 현재 한국어로 읽히는 뜻을 대조한다. 형태·문법이 맞아도 행동, 대상, 관계, 선택지의 차이를 부적절하게 전달할 수 있다.

사용처별 `context_reviews`에 의미 맥락 ID, `korean_reading`, `fit`, 판단 이유와 제품 근거를 남긴다. 현재까지 노출된 정보로 **무슨 행동이나 대상이 떠오르는지**와 **실제로 무엇이 일어나는지**를 구분한다. `korean_reading`은 검토자의 해석이며 실제 사용자의 발언이나 관찰 결과로 꾸미지 않는다. 이후 화면·코드·세션 설명을 알고서만 성립하는 해석을 사용자에게 분명한 표현이라고 판정하지 않는다. 판정 기준은 외부 출처의 주장·범위·예외에서 가져온다.

- 단어의 뜻과 결합이 실제 행동·대상에 맞는가? 사전의 대응어를 안다는 사실만으로 현재 사용처에서 적절하다고 하지 않는다.
- 관용 표현이나 비유의 표면을 옮겨 원래 전달 의도가 흐려지지 않았는가?
- 주변 질문·선택지·변수의 지시 대상과 앞뒤 단계가 같은 뜻으로 이어지는가?
- 내부 기능명이나 모호한 동사가 사용자가 하려는 일을 가리지 않는가?
- 같은 표현의 다른 사용처에서도 뜻이 같은가? 실제 연결 기능의 ‘연결’처럼 해당 과업에 맞는 표현까지 바꾸지 않는다.

사용자가 든 `Keep editing → 계속 수정`은 진단 필요성을 설명하는 사례이지 금지 대응표가 아니다. 편집 이탈을 취소하는지, 중단한 작업을 다시 여는지, 무엇을 고치는지 먼저 확인한다. 그 동작을 사용자가 현재까지 받은 안내와 표현만으로 이해할 수 있는지도 별도로 판단한다. 실제 영문 자료가 제공될 때만 보조로 참고하며 번역 기원은 단정하지 않는다.

이후 LT-01~04로 구문·복수·전치사구·일한 간섭을 보조 점검한다. 검색에 걸리지 않거나 문법이 맞다는 이유로 의도·어휘 검토를 생략하지 않는다. 일상적인 피동, 명사형 레이블, 익숙한 전문 용어는 그 자체로 오류가 아니다.

`clear`는 검토한 유형에서 모든 사용처가 적합한 경우다. `candidate`는 출처와 맥락 대조로 문제를 설명할 수 있는 후보이며 번역 기원을 증명하거나 자동 교정을 허용하지 않는다. `uncertain`은 필요한 맥락·근거가 없어 판단할 수 없는 사용처가 있다는 뜻이다. 어휘 적합성과 별개인 잘못된 성공 안내·불필요한 중복은 해당 UX·한국어 규칙으로 다루며 모두 번역투라고 부르지 않는다.

첫 수정 전에 `diagnosis.json`을 저장하고 `--diagnosis-only`로 검사한다. 원문 대장과 진단을 보존한다. 뒤늦게 사용처의 뜻이 다르다는 사실을 알게 되면 기존 기록을 남기고 ID 대응·추가 근거를 갖춘 새 대장과 진단을 만든다. 새 진단을 검사하기 전에 그 판단에 의존하는 수정을 진행하지 않는다.

## 뜻의 문제를 해결한 다음 표현을 다듬는다

`candidate`의 수정·유지 이유를 `diagnosis_resolution`에 연결한다. 어떤 뜻의 차이를 해소했는지, 어떤 예외·제약 때문에 그대로 두는지 설명한다. 어미만 바꿔 확인한 의미 문제를 해결했다고 하지 않는다. `uncertain`은 새 근거로 진단을 갱신하기 전까지 `blocked` 또는 `excluded`로 보존한다.

선행 맥락 누락 여부를 먼저 판단한다. 필요한 안내가 이전 경로에 없었다면 `ux_findings`에 흐름 문제와 적절한 제공 시점을 기록한다. 그 문제를 현재 문구의 설명 추가로 대신하지 않는다. 표현 자체로 해결할 수 있는 내용이 확정되면 `KO-*` 근거로 한국어를 다듬는다. 보존할 것은 확인한 제품 의미이며 사실과 다른 기존 주장을 유지하라는 뜻이 아니다. 없던 번역투나 어법 오류를 만들어내거나 버튼 어형을 다루는 KO-05를 링크의 근거로 자동 확대하지 않는다.

출처 하나가 UX와 한국어를 함께 다뤄도 적용한 주장과 책임을 구분한다. 자연스러운 어순을 근거로 필수 안내를 삭제하거나, 필요한 안내를 근거로 특정 높임말을 강제하지 않는다.

목적지 화면을 읽지 못했어도 신뢰할 사양에 이동 목적이 명시돼 있다면 그 사실만으로 판단 가능한 레이블을 부분 수정할 수 있다. 목적지 상태·결과·복구까지 확인한 것으로 취급하지 않으며 해당 경로는 보류한다. 확인하지 못한 사실에 의존하는 변경은 적용하지 않는다.

## 출처를 적용하는 범위

`sources.lock.json`은 전체 증적 레지스트리의 고정 커밋과 SHA-256을 가리킨다. `scripts/kuw evidence`로 검증된 파일을 읽고, 규칙의 `sources`에 해당하는 항목을 찾는다. 각 항목의 `locator`, `claim`, `scope`, `limitations`, `verification`을 확인한다. 필요한 경우 원문 링크에서 해당 구절을 더 읽는다.

`partial` 자료는 조사 후보이며 이 버전의 실행 규칙을 정당화하지 않는다. 규칙이 요구하는 주장이 증적에 없거나, 원문·증적을 확인할 수 없거나, 적용 범위가 현재 UI와 다르면 해당 판단을 보류한다. URL이 있다는 사실만으로 근거가 충족되지는 않는다.

공식 지침은 해당 플랫폼·서비스의 지침이다. 제품 사례는 그 사용 환경의 관찰이다. 개인 원저술은 전문가의 제안이며 보편 규범이나 실험 결과로 바꾸어 말하지 않는다. 국어 규범은 표기의 근거이지 특정 말투의 UX 효과를 증명하지 않는다.

출처 간 충돌은 다수결로 해결하지 않는다. 대상 사용자, 제품의 문서화된 말투, UI의 목적, 적용 조건을 대조한다. 조건으로 해결되지 않는 문체 선택은 기존 의미를 보존하고 보류 이유를 남긴다.

## 수정과 보존

문자열 전체 검색·일괄 치환을 피한다. 같은 글자라도 퍼널의 역할이 다르면 각자 판단한다. 공용 키가 다른 맥락을 겸해 한 문구로 해결할 수 없으면 사용처별 분리가 필요한 이유를 보고한다. 이미 허용된 범위의 문구 리소스 분리는 모든 호출부와 테스트를 함께 갱신하고 행동은 유지한다.

흐름 구현이 허용되어 원래 없던 문구를 추가한다면 `additions`에 별도로 기록한다. 기존 문구의 원문·진단·결정은 그대로 보존하고, 새 문구에는 허용 범위·추가 이유·연결된 흐름 문제·사용처별 검토를 남긴다. 새 화면과 문구는 `recheck`에서 확인한다. 자세한 형식은 [감사 기록 형식](audit-format.md)을 따른다.

번역 키·API 식별자·분석 이벤트·오류 코드를 문장으로 오인해 바꾸지 않는다. 명령형 대화상자, 화면 텍스트, 접근성 이름이 같은 행동을 가리키는지 함께 확인한다. 원문 해시나 현재 텍스트를 다시 대조한 뒤 패치해 다른 변경을 덮어쓰지 않는다.

동적 문장은 실제 렌더링 결과로 확인한다. 변수 이름·개수·타입, ICU 선택 분기, 복수형, 숫자·날짜 형식, 태그 구조를 보존한다. 자동 검사가 다루지 못하는 문법과 의미는 수동 검토 항목에 남긴다.

## 완료 판단

검증 도구의 성공은 기록이 구조적으로 일치한다는 의미다. 필수 사용자 관점 기록, 사용처와 경로, 추가 문구와 미해결 문제의 연결도 검사한다. 모든 문구를 찾았거나 의미가 올바르다는 자동 증명은 아니다.

완료를 보고하려면 발견한 범위의 모든 문구와 사용처에 판정이 있고, 전체 퍼널과 분기가 읽혔으며, 사용자 관점 기록과 코드·내용·화면 검증을 실제로 확인해야 한다. 실행 환경이 없어 화면 확인을 못 했거나 경로를 재현하지 못했다면 `unresolved`에 남기고 부분 결과로 보고한다. 남은 흐름 문제도 같은 목록에 연결하며 윤문을 마쳤다는 이유로 전체 UX가 개선되었다고 하지 않는다.

변경 후 실제 퍼널을 다시 따라가며 앞 단계의 약속과 뒤 단계 결과, 반복 용어, 상태 간 구분, 다음 행동의 실행 가능성을 점검한다. 고친 표현도 독자가 필요한 뜻을 알 수 있는지 다시 읽는다. 좁은 화면, 긴 변수 값, 스크린리더 이름도 확인한다. 재실행 시 이미 적합한 문구를 근거 없이 다시 바꾸지 않는다.
