# 독자가 무엇을 알 수 있는지 확인하기

문법이 맞고 내부 절차와 일치해도 독자에게 뜻이 분명한 문장은 아닐 수 있다. `KO-02·06·08`, `UX-09·10·12`의 외부 근거로 전문 용어, 추상적인 명사 묶음, 구체적인 대상이 없는 절차 설명을 확인한다. 한국어 어휘 판단에는 한국어 자료를 함께 적용한다.

## 누구에게 필요한 문구인가

현재 문구를 읽는 사람과 그 사람이 여기서 알아야 할 것을 먼저 정한다. README를 읽는 개발자, 제품을 사용하는 사람, 내부 감사 기록을 읽는 검토자는 같은 독자가 아니다. 한 분야의 전문가라는 이유로 다른 분야의 절차·분류·용어까지 안다고 가정하지 않는다. 실제 조사 자료가 없으면 독자와 읽는 목적을 검토 가설로 표시한다.

요청된 README·설치 안내·도움말도 같은 방식으로 검토한다. 요청받지 않은 문서나 내부 기록까지 일괄 윤문하지 않는다. 스키마 이름·명령어·API 식별자·정확성이 필요한 전문 용어는 일반 안내문과 구분한다.

## 표현을 고르기 전에 확인할 것

1. **독자의 질문:** 이 위치에서 무엇을 알고 결정하려는가? 소개에서는 무엇을 해 주는지, 설치에서는 어디에 무엇을 입력하는지, 이용 조건에서는 어떤 자료에 어떤 조건이 적용되는지처럼 문구의 목적을 적는다. 기능이 없는 곳에 행동을 억지로 만들지 않는다.
2. **현재 문구의 답:** 앞서 제공된 정보와 현재 문구만으로 알 수 있는 대상·행동·결과·조건을 평이하게 적는다. 원문을 반복하거나 내부 기획 설명을 보태야만 답할 수 있으면 그 빈틈을 남긴다. 이는 검토자의 해석이며 실제 독자의 이해를 관찰한 결과가 아니다.
3. **낱말과 결합:** 특정 독자에게 불필요한 전문 용어인지, 추상적인 명사와 범용 동사가 구체적인 일을 가리는지, 수식어가 가리키는 대상이 있는지 확인한다. 쉬운 낱말로만 썼거나 짧다는 이유로 통과시키지 않는다.
4. **유지할 이유:** 이 독자에게 익숙하거나 정확성을 위해 필요한 용어라면 유지한다. 앞선 안내가 뜻을 구체적으로 밝혀 주는지도 확인한다. 모든 한자어·명사형·전문 용어를 바꾸지 않는다.

기존 문구의 `context_reviews.korean_reading`에는 독자가 받을 수 있는 답을, `reason`과 최종 `occurrence_reviews.note`에는 그 답의 단서와 남은 모호함을 기록한다. 새 문구는 `additions.occurrence_reviews`에서 같은 내용을 점검한다. `keep`도 해당 위치의 이유가 필요하다. 서로 다른 안내·명령어·이용 조건에 같은 일반 문장을 복사해 검토 근거로 삼지 않는다.

## 표현 수정과 안내 위치를 구분하기

필요한 사실과 안내가 이미 있는데 내부 분류나 추상어로 설명했다면 그 대상을 구체적으로 표현한다. 독자에게 필요한 개념·조건을 앞서 제공하지 않았다면 [사용자 관점 점검](user-perspective.md)에 따라 흐름 문제로 기록한다. 제목이나 버튼을 길게 풀어 쓰는 것으로 빠진 단계를 대신하지 않는다.

기술·법률 용어가 정확성에 필요하면 뜻과 적용 범위를 보존한다. 설명을 쉽게 쓴다는 이유로 권리의 주체, 이용 대상, 허용 범위, 조건이나 예외를 바꾸지 않는다. 원문 링크나 라이선스 본문을 확인할 수 없으면 관련 판단을 보류한다. 권리를 가진 사람이 항상 작성자라고 가정하지 않는다.

## 문서의 약속과 실행 조건 점검

README·설치 안내·도움말은 문단 순서와 독자의 작업 순서가 다를 수 있다. 해당 문서의 과업에 따라 읽기 → 선택·명령 실행 → 생성물 사용·수정 → 이후 작업을 따라간다. 전체 문서를 읽은 검토자가 뒤쪽 제약을 안다는 이유로, 앞서 선택하는 독자도 안다고 보지 않는다. 정상 경로와 실제로 안내한 다른 경로·조건을 확인하며 가상의 모든 실패를 늘어놓지는 않는다.

행동 가능성·조건·보호 범위·결과를 약속하는 문구는 서로 떨어져 있어도 함께 대조한다. 먼저 `korean_reading`과 행동 전 예상에 독자가 받을 수 있는 답을 남기고, 코드·사양에서 성립 조건과 예외를 확인한다. 내부 사실을 먼저 읽었다면 그 순서를 밝힌다. 다음은 `UX-04·09·12·13`, `KO-08`을 문서에 적용하는 점검 방법이며 새 금칙어나 고정 문구 규칙이 아니다.

| 문서가 설명하는 것 | 확인할 차이 |
|---|---|
| 나중에 할 수 있는 작업 | 그사이 문서가 안내한 사용·편집을 해도 가능한가? 이후 작업을 막는 조건이 있다면 처음 선택을 바꾸어야 하는 시점은 어디인가? |
| 실행 조건과 사용 예 | 실제 필수 조건인가, 가능한 여러 방법 중 예시인가? 예시를 필수 절차처럼 좁히거나, 조건을 없애 무조건 가능하다고 넓히지 않았는가? |
| 보존·교체하는 범위 | 독자가 자신의 파일·화면에서 경계를 식별할 단서가 있는가? 무엇이 유지되고 무엇이 바뀌는가? 내부 구간 이름을 이해했다는 가정만으로 통과시키지 않는다. |
| 생성·준비·실행 결과 | 무엇이 어디에 생기며 누가 실행하는가? 파일 생성, 화면 표시, 서버 실행을 구별할 수 있는가? 이미 주변 안내로 분명한 내용은 반복하지 않는다. |

주장별로 원문 위치, 독자에게 보이는 조건 위치, 확인한 실제 조건·예외를 `context_reviews.reason`과 제품 근거에 연결한다. 마지막에 조건이 나왔다는 사실만으로 앞선 약속과의 대조를 끝내지 않는다. 선택을 바꿀 제약이 늦게 나온다면 `ux_findings.first_needed`에 처음 필요한 위치를 남기고, 앞의 약속과 뒤의 설명을 함께 참조한다. 명령 앞에 경고를 옮겼어도 더 앞선 선택에 필요한 안내가 빠져 있다면 그 문제는 열어 둔다.

보호 범위처럼 독자가 직접 식별해야 할 대상을 설명할 때는 실제 표식·경로·화면 이름을 확인한다. 확인한 예시나 설명이 더 필요하면 추가를 제안하되 기존 외국어 표기를 번역하거나, 없는 표식·복구 방법을 만들지 않는다. 문서 재배치·새 안내의 실제 적용은 허용 범위에 따르고, 미적용 제안은 해결된 수정으로 기록하지 않는다. 대상 독자에게 익숙한 용어와 문맥상 분명한 예시는 유지할 수 있다.

고친 문구에 같은 기준을 적용하는 절차는 [4. 재검증](verification.md)에서 읽는다. 지금은 원문의 진단과 미해결 맥락을 확정한다.
