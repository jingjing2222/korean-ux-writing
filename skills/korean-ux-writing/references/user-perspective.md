# 사용자가 알 수 있는 정보로 과업을 따라가기

제품의 전체 동작과 사용자의 이용 맥락은 다르다. 동작을 알고 설명할 수 있다는 이유로 좋은 UX라고 판단하지 않는다. 사용자의 목적, 진입 계기, 지금까지 접한 안내, 현재 선택과 예상 결과를 기준으로 검토한다. 구현·정책·세션의 설명은 사실 확인과 작업 제약에만 사용한다.

이 문서는 외부 UX 근거를 적용하는 운영 절차다. 정보의 필요성은 UX-09·11, 사용자에게 제공된 정보와 안내 시점은 UX-12·13의 고정 증적을 읽어 판단한다. 이 절차 자체나 검토자의 취향을 품질 기준으로 삼지 않는다.

## 지식을 분리한다

| 구분 | 허용되는 사용 |
|---|---|
| 사용자 과업과 이용 상황 | 실제 조사·관찰·사용 시나리오의 출처를 남긴다. 자료가 없으면 검토용 과업 가설이라고 표시한다. 구현된 기능에 맞춰 사용자의 목적을 만들어내지 않는다. |
| 해당 경로에서 제공된 정보 | 실제 진입 경로, 앞서 노출된 안내, 현재 화면·접근성 안내, 그 시점에 찾을 수 있는 도움말을 위치와 함께 기록한다. |
| 검토자만 아는 정보 | 작업 요청자의 설명, 세션 대화, 코드·식별자·설계 의도, 다른 분기와 이후 화면은 현재 사용자의 지식에 넣지 않는다. |

제공된 정보와 읽고 기억하고 이해한 정보는 다르다. 특정 전문 지식이 필요한 제품이라면 대상 사용자의 실제 조건을 확인하며, 모든 사용자를 초보자로 가정하거나 허구의 페르소나를 만들지 않는다. 처음 진입·재방문·딥링크에서 제공되는 맥락이 다르면 별도 경로로 점검한다.

같은 화면에 도착해도 경로별 사전 안내가 달라 해석이나 필요한 정보가 달라지면 `funnel.nodes`, `meaning_contexts`, `occurrences`를 경로별로 구분한다. 문구의 뜻은 같다면 같은 inventory ID에 여러 occurrence를 연결할 수 있다. 각 occurrence에 진단과 최종 검토를 남기며, 한 경로의 적합 판정으로 다른 경로를 덮지 않는다. 맥락이 동등해 합치는 경우에는 함께 검토한 경로와 동등한 이유를 기록한다.

## 정답을 알려주지 않고 순서대로 점검한다

가능하면 구현 설명을 읽기 전에 실제 화면부터 살핀다. 독립 검토가 가능하면 새 검토자에게 세션 이력·코드·정답 경로·예상 문제를 전달하지 않고, 과업과 사용자에게 보이는 자료만 준다. 진행에 따라 다음 화면을 제공하고 예상은 다음 화면을 공개하기 전에 저장한다. 여러 화면을 한꺼번에 보여주고 독립적인 첫인상 검토라고 부르지 않는다.

이미 제품 사실을 읽었다면 모르는 척하지 않는다. 알고 시작한 사실을 기록하고, 독립 검토자를 사용할 수 없는 경우 그 한계를 남긴다. 에이전트 검토는 실제 참여자의 사용성 테스트를 대체하지 않는다.

1. 사용자가 달성하려는 결과로 과업을 제시한다. 클릭 순서, 정답 버튼명, 개발자의 해결책으로 유도하지 않는다. 널리 쓰는 표준 용어까지 억지로 돌려 말하지 않는다. 과업 가설과 실제 사용자에게서 확인한 요구를 구분한다.
2. 각 단계에서 현재까지 제공된 정보만으로 다음을 기록한다. **무엇을 하려는지, 할 일을 찾을 수 있는지, 선택지의 차이가 무엇인지, 선택하면 무엇이 일어날 것으로 읽히는지, 무엇이 부족한지.** 행동 전 예상을 먼저 저장한다.
3. 선택 후의 화면과 결과를 확인한다. 무엇이 바뀌었는지, 목표에 가까워졌는지, 기다리거나 다음 행동을 해야 하는지 알 수 있는지 대조한다. 뒤늦게 알아낸 사실로 행동 전 기록을 고치지 않는다.
4. 취소·돌아가기·실패·복구와 다른 진입 경로에서도 반복한다. 이후 전체 퍼널의 실제 동작을 코드·사양과 대조하되 사용자에게 없던 안내를 노출된 것으로 바꾸지 않는다.

문구가 DOM이나 소스에 있다는 이유만으로 보이고 발견된다고 하지 않는다. 접힘·스크롤·모달 순서·지속 표시·접근성 연결을 실제로 확인한 범위를 남긴다. 정적 자료만 있으면 예상 가능한 문제를 기록하고 렌더링·발견 가능성·참여자 반응은 미확인으로 둔다.

## 선행 맥락이 없으면 흐름 문제부터 다룬다

현재 문구가 이해되지 않는 이유를 먼저 구분한다. 필요한 맥락을 이미 전달받았지만 표현이 뜻을 잘못 가리키는지, 아니면 사용자가 아직 알아야 할 대상·조건·개념을 전달받지 못했는지 확인한다.

**앞서 필요한 맥락을 제공하지 않은 문제는 흐름 개선 사항이다. 현재 레이블·설명·툴팁에 내용을 덧붙여 해결한 것으로 처리하지 않는다.** 사용자가 처음 그 정보를 필요로 하는 단계와 그 이유를 찾아, 진입 안내·단계 순서·선택지 구성·확인 시점 중 무엇을 개선해야 하는지 외부 근거와 함께 제안한다. 딥링크가 선행 단계를 건너뛰면 그 진입 경로도 다룬다. 불필요한 온보딩을 일괄 추가하거나 모든 정보를 첫 화면에 모으라는 뜻은 아니다.

- `copy`: 필요한 맥락과 기능은 제공되지만 표현이 부정확하거나 모호하다. 해당 문구를 다듬고 다시 점검한다.
- `flow`: 선행 안내·정보의 순서·경로·발견 가능성·피드백·복구 수단에 문제가 있다. 문제 단계와 사용자에게 필요한 맥락, 개선이 필요한 위치를 기록한다. 현재 문구에 설명을 추가하는 것으로 종결하지 않는다.
- `mixed`: 표현 문제와 흐름 문제가 함께 있다. 문구로 고친 부분과 아직 남은 흐름 문제를 따로 남긴다.

검토 범위가 윤문이면 독립적으로 안전한 문구 개선만 적용하고 흐름 변경안을 보고한다. 구현까지 허용되었을 때만 동작·구조를 고친다. 어느 경우든 처리하지 않은 흐름 문제를 문구 개선 성과에 포함하지 않는다. 이미 제공된 맥락의 짧은 재확인이 필요한 경우와 선행 맥락이 전혀 없는 경우를 구분한다.

## 남길 기록

첫 문구 수정 전에 `user-perspective.json`을 저장하고 `diagnosis.json`의 `user_perspective_ref`로 연결한다. 수정 후 결과는 원래 단계 기록을 덮어쓰지 않고 별도 `recheck`에 추가한다. 형식은 아래 필드를 갖춘 간결한 JSON으로 유지한다.

- `method`: 실제 참여자 관찰, 사용자 화면만 받은 독립 에이전트 검토, 또는 내부 정보를 알고 한 전문가 검토 중 실제 방식. 관찰 자료가 없으면 참여자 발언·성공률·선호를 만들지 않는다.
- `task`: 사용자의 목적, 근거, 알려진 이용 상황과 아직 가정인 사항.
- `reviewer_knowledge`: 시작할 때 이미 알던 내부 정보와 독립 검토자에게 제공한 자료.
- `paths`: 각 진입 경로와 단계 순서. 단계마다 `node_id`, 해당 `occurrence_ids`, `available_information`과 확인 위치, `before_action`의 해석·선택·예상·미확인점, `after_action`의 실제 결과와 차이를 기록한다. 도착 전부터 결과를 알았다면 명시한다.
- `ux_findings`: 문제 ID, 해당 경로·단계·문구, `copy/flow/mixed`, 부족한 맥락, 그 맥락이 처음 필요한 단계와 이유, 확인한 사실, 적용 UX 규칙·출처, 개선 제안, 적용한 범위와 남은 문제.
- `recheck`, `limitations`: 수정 후 같은 과업을 다시 확인한 결과와 재현·관찰하지 못한 범위.

`meaning_contexts`는 실제 과업과 동작의 기록이고, 이 파일은 사용자에게 전달된 정보와 그 한계의 기록이다. 두 기록을 대조해 `korean_reading`을 쓰되 제품 사실을 읽어야만 성립하는 해석을 사용자의 이해로 올리지 않는다. 필요한 선행 맥락이 빠진 사실을 확인했다면 그 흐름 문제는 확정해서 기록하고, 어휘 자체의 적합성을 판단할 수 없으면 진단은 `uncertain`으로 둔다.

이 부가 기록은 네이티브 v2 검사기가 검증하지 않는다. 수동으로 모든 발견된 사용처·경로와 연결됐는지, 행동 전 예상에 이후 정보가 섞이지 않았는지 확인한다. 남은 `flow/mixed` 문제와 미확인 상태는 최종 감사의 `unresolved`에도 연결한다. 검사 통과나 다른 에이전트의 동의만으로 사용자 이해·과업 성공을 입증했다고 보고하지 않는다.
