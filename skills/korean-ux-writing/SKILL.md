# Korean UX Writing

**사용자가 자신의 목적과 지금까지 받은 안내만으로 다음 행동과 결과를 이해할 수 있는지 먼저 본다.** 필요한 맥락이 앞서 제공되지 않았다면 흐름 개선 사항으로 다룬다. 그다음 표현이 뜻에 맞는지 진단하고 윤문한다. 문법이 맞고 기능을 짐작할 수 있어도, 한국어에서 다른 행동·대상·관계를 떠올리게 하는 표현은 놓치지 않는다.

**검토자가 아는 맥락으로 사용자가 모르는 내용을 메우지 않는다.** 전체 퍼널은 실제 동작을 확인하기 위해 읽는다. 이해 가능성은 사용자가 그 경로에서 지금까지 접할 수 있는 정보로 판단한다. 세션의 설명, 내부 구현, 다른 분기나 다음 화면에서만 알 수 있는 사실로 현재 안내를 합리화하지 않는다.

**영어 원문이 없는 한국어 제품을 기본으로 검토한다.** 영어를 먼저 개발했거나 현재 문구가 번역문이라고 가정하지 않는다. 한국어로 처음 작성한 문구도 퍼널의 뜻과 어긋날 수 있다.

제품 코드·사양은 실제 동작을 확인하는 자료다. UX 근거는 필요한 안내를 결정하고, 한국어·현지화 근거는 그 안내가 한국어로 적절하게 전달되는지 판단하는 데 쓴다. 프로젝트 읽기 권한이 필요하다. 검증 도구의 플랫폼별 실행 경로는 [실행 안내](references/runtime.md)를 따른다.

## 시작할 때

1. [워크플로](references/workflow.md)와 [사용자 관점 점검](references/user-perspective.md)을 읽는다. 가능한 경우 구현 설명을 읽기 전에 사용자에게 보이는 첫 화면부터 과업을 따라가고 행동 전 예상과 실제 결과를 분리해 기록한다. 이미 내부 맥락을 알면 그 한계를 밝힌다. 파일 하나를 요청받아도 관련 퍼널의 앞뒤 맥락과 분기를 확인한다.
2. [규칙](references/rules.json), [한국어 맥락 적합성·번역투 진단 기준](references/translationese.json), [독자 이해 점검](references/reader-language.md)을 읽고 아래 도구로 고정된 증적을 가져온다. 적용할 출처의 확인 위치·주장·조건·예외를 읽는다.
3. [감사 기록 형식](references/audit-format.md)의 **version 2**로 원문 대장을 만든다. 문구를 발견하는 대로 고치거나 대안부터 만들지 않는다.

```sh
<skill-directory>/scripts/kuw evidence --out .reports/korean-ux-writing/sources.json
```

`<skill-directory>`는 설치된 이 파일의 디렉터리다. 원본 체크아웃에서는 `--source docs/evidence/sources.json`으로 같은 해시의 로컬 증적을 사용할 수 있다. 설치된 스킬 밖에 원본 레포가 있다고 가정하지 않는다.

## 1. 사용자 경로를 따라가고 전체 동작과 대조한다

범위가 없으면 프론트엔드 전체를 조사한다. 라우트·화면·상태·권한·기능 플래그와 공용 컴포넌트의 사용처를 찾는다. 한국어 문자열 검색만으로 범위를 확정하지 않는다.

사용자 관점 점검에서 진입 목적, 앞 단계의 안내·약속·입력, 현재 선택과 예상 결과를 순서대로 남긴다. 이후 조건별 전이, 직후와 최종 결과, 취소·뒤로 가기·실패·재시도를 전체 동작과 대조한다. 호출부, 상태 관리, 검증, 요청·응답 처리, 번역 리소스와 실제 화면은 이 사실 확인에 쓴다. `setState`나 `savePreference` 같은 핸들러 이름만으로 사용자의 과업을 설명하지 않는다.

같은 문구를 공유하는 모든 퍼널을 확인한다. 관련 코드나 결과를 확인할 수 없으면 그 경로와 의존하는 판단을 보류하고, 확인 가능한 다른 경로를 계속 검토한다.

## 2. 문구와 사용처를 대장에 고정한다

제목·본문·버튼·링크·입력 안내·오류·로딩·빈 화면·알림·모달·접근성 이름·대체 텍스트·문서 제목을 수집한다. 동적 문장과 분기, 서버/CMS, 이미지 속 문구도 조사하고 사용자 콘텐츠는 구분한다.

**소스 키와 의미 단위는 다르다.** 같은 키라도 퍼널에서 뜻이 다르면 진단 전에 사용처별 inventory ID로 나누고 원래 키·문구·위치를 남긴다. 실제 코드는 아직 바꾸지 않는다. 뜻이 같은 공유 문구는 한 ID 아래 모든 사용처를 연결한다. 조각난 JSX는 하나의 문장으로 읽되 위치를 모두 보존한다.

## 3. 현재 표현에 끌려가지 않고 안내 의도를 재구성한다

사용자 과업의 근거 또는 명시한 과업 가설과 `UX-*` 기준으로 필요한 안내를 정하고, 확인한 동작을 대조해 `meaning_contexts`를 작성한다. 별도 `user-perspective.json`에는 그 경로에서 사용자에게 노출된 정보, 행동 전 해석·예상, 실제 결과와의 차이를 남긴다. 제품 사실 기록을 사용자 지식 기록으로 대신하지 않는다. 화면·상태별로 다음을 평이하게 설명한다.

- 사용자가 이 흐름에서 이루려는 목적.
- 앞서 받은 안내와 약속, 이미 입력하거나 선택한 내용.
- 지금 알아야 하거나 결정해야 할 것.
- 행동 직후의 결과와 이후의 결과·제약.

현재 한국어, 영어 낱말, 키 이름을 반복하는 대신 **무엇을 누구에게 왜 알려야 하는지** 적는다. 아직 개선 문구를 만들지 않는다. 앞선 안내가 해당 진입 경로에 실제로 있었는지, 지금 찾을 수 있는지 확인한다. 노출됐다는 사실만으로 읽고 기억하고 이해했다고 가정하지 않는다. 코드나 요청자의 설명으로 추론한 목적은 실제 최종 사용자 조사 결과와 구분한다.

기존 안내가 실제 동작과 다르면 원래 주장·확인한 사실·확인 위치를 대조한다. 접수와 완료, 다음 단계 이동과 실제 실행을 구별한다. 없는 원인·복구 방법·확정 결과를 만들지 않는다. 맥락이 없으면 무엇이 미확인인지 기록한다.

## 4. 현재 한국어로 읽히는 뜻과 대조한다

먼저 `LT-05`로 각 사용처를 검토한다. `context_reviews`에 해당 의미 맥락과 사용처를 연결하고, 현재 표현으로 읽히는 뜻(`korean_reading`), 적합성(`fit`), 이유와 사실 근거를 남긴다. `intent`와 `korean_fit`에는 전체 판단을 요약한다.

현재 문구의 독자가 여기서 알아야 할 것과 실제로 알 수 있는 답을 대조한다. 내부의 절차·분류·전문 용어를 정확히 옮겼어도 대상·행동·결과가 드러나지 않으면 지나치지 않는다. README나 도움말을 요청받았다면 그 문서의 독자를 제품의 최종 사용자나 내부 검토자와 구분한다. 구체적인 판단은 [독자 이해 점검](references/reader-language.md)을 따른다.

사전적으로 맞는 단어라도 이 상황의 행동·대상·관계와 어긋나는지, 내부 용어·영어 관용 표현·범용 동사를 따라 쓰느라 안내 의도가 흐려졌는지 본다. 주변 제목·설명·선택지를 해당 경로에서 노출된 순서로 대조한다. 사용자가 행동을 찾고, 선택지의 차이와 결과를 예상하고, 이후 진행 상태를 알아볼 수 있는지 점검한다. 미래 화면의 설명으로 현재의 빈틈을 메우지 않는다. 한국어로 읽히는 뜻은 검토자의 해석이며 실제 사용자 반응을 관찰한 결과와 구분한다.

한국어 문구와 사용자에게 전달된 맥락으로 적합성을 판단하고 실제 동작은 별도로 대조한다. 영문을 찾아내거나 상상해 복원하는 단계를 두지 않는다. 실제 영문 자료가 제공된 경우에만 보조로 대조하며 번역 기원은 단정하지 않는다. 문법적으로 맞음, 원문 낱말과 대응함, 기존 제품에서 쓰임, 영어 원문이 없음은 `clear`의 충분한 이유가 아니다. 익숙한 전문 용어나 실제 연결 기능의 ‘연결’처럼 적절한 표현은 유지한다.

이어 `LT-01~04`의 구문·복수·전치사구·일한 간섭을 보조 확인한다. 형태 검사를 의도·어휘 진단의 대용으로 쓰지 않는다. 각 문구를 `candidate`·`clear`·`uncertain`으로 기록하고 첫 수정 전에 저장한다.

```sh
<skill-directory>/scripts/kuw audit .reports/korean-ux-writing/diagnosis.json --diagnosis-only
```

검사기는 사용처·의미 맥락의 연결과 판정 일관성을 확인한다. 문구의 자연스러움이나 해석의 타당성은 증명하지 않는다. `uncertain` 항목은 새 근거로 진단을 갱신하기 전까지 고치지 않는다. 원래 진단을 보존하고 갱신 사유를 남긴다.

## 5. 뜻의 어긋남을 바로잡은 뒤 윤문한다

진단에서 확인한 문제부터 해결한다. `candidate`를 고치거나 유지할 때는 `diagnosis_resolution`에 어떤 해석 차이를 어떻게 해소했는지, 또는 왜 그대로 두는지 적는다. 어미나 길이만 바꿔 의미 문제가 해결됐다고 하지 않는다.

그다음 `KO-*` 근거로 어휘·어순·호흡·높임·조사·띄어쓰기를 다듬는다. 특정 영어의 고정 대체어, 임의 금칙어·점수, 해요체·능동형·긍정형의 일괄 강제는 사용하지 않는다. 문서화된 제품 용어와 말투는 제약으로 확인하며, 기존 문구 자체를 좋은 한국어의 증거로 삼지 않는다.

보존할 것은 확인한 제품의 의미다. 조건·예외·부정·책임 주체·확정성·금액·기간·단위·변수·ICU 분기·접근성 연결을 지킨다. 잘못된 기존 안내까지 보존하라는 뜻은 아니다. 선행 맥락이 없거나 안내가 너무 늦은 문제, 선택·피드백·복구 수단이 없는 문제는 `ux_findings`에 기록한다. 필요한 맥락을 처음 제공해야 하는 단계와 이유를 제안하며, 현재 문구에 설명을 덧붙여 해결 처리하지 않는다. 윤문 범위를 넘는 동작·구조 변경은 별도로 보고한다.

좋은 문구는 `keep`, 근거나 맥락이 부족한 문구는 `blocked`로 남긴다. 기준이 부족하면 출처 없는 새 규칙을 만들지 않는다.

허용된 흐름 구현으로 새 안내를 추가했다면 `additions`에 따로 기록한다. 없던 원문이나 수정 전 진단을 만들어 기존 대장에 넣지 않는다. 추가 이유·허용 범위·관련 흐름 문제와 각 사용처의 UX·한국어 근거를 연결하고 새 경로를 다시 검토한다.

## 6. 같은 퍼널에서 다시 검증한다

원문·진단·결정을 1:1로 대조하고 모든 사용처와 분기를 다시 읽는다. 수정 전 점검 기록을 보존한 채 설명이나 정답 경로를 주지 않고 같은 과업을 다시 점검한다. 고친 문구도 독자의 질문에 구체적으로 답하는지 확인한다. 앞 단계의 약속, 뒤 단계의 결과, 선택지 간 구별과 용어가 맞는지 확인한다. 가능한 환경에서 실제 화면·줄바꿈·접근성·동적 값도 확인한다.

```sh
<skill-directory>/scripts/kuw audit .reports/korean-ux-writing/audit.json --require-complete
```

검사는 기록과 토큰의 일관성, 사용자 관점 기록의 존재와 연결, 추가 문구와 남은 흐름 문제의 연결을 확인한다. 실제 점검 순서와 판단의 타당성은 따로 검토한다. 해결되지 않은 UX 문제와 실행하지 못한 검증은 최종 감사의 `unresolved`에도 연결한다. 이를 범위에서 빼서 완료율을 높이지 않는다.

## 결과 보고

검토 범위, **사용자에게 전달되지 않았던 정보와 의도·표현의 차이**, 수정·유지·보류 수, 남은 UX 문제와 검증 결과를 짧게 알린다. 상세 대장에는 원문·수정문·퍼널 맥락·사용자 관점 점검·진단·UX 근거·한국어 근거·사실 확인 위치를 남긴다. 실제 참여자를 관찰하지 않았다면 에이전트의 사용성 사전 점검이라고 밝힌다. 미확인 사항이 있으면 부분 결과로 보고한다.
