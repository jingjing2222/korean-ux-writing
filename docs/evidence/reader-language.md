# 독자에게 필요한 뜻을 전달하는 근거

내부 절차를 정확히 설명한 문장도 독자가 무엇을 맡기고, 어떤 결과를 받고, 무엇을 이용할 수 있는지 알려 주지 못할 수 있다. 번역투·문법 검사와 별도로 독자와 정보의 목적을 확인하는 근거다.

| 원문에서 확인한 내용 | 확인 위치와 출처 | 적용할 때의 한계 |
|---|---|---|
| 독자가 누구인지, 이미 아는 것과 알아야 할 것, 가질 질문을 확인한다. 작성자에게 필요한 정보와 독자에게 필요한 정보를 구분한다. | 국립국어원 『쉬운 공문서 쓰기 길잡이』, PDF 36~39쪽. [SRC-043](sources.md#src-043) | 공문서의 문체나 인구통계에 따른 추정을 UI에 적용하지 않는다. 이 부분의 확인이며 책 전체 검증이 아니다. |
| 어느 기능에나 붙일 수 있는 포괄적인 소개는 실제 기능을 전달하지 못한다. 사용하는 사람에게 도움이 되는 표현을 고른다. | 삼성 「Designing Words」, 기능 소개 사례와 전문 용어의 예외. [SRC-008](sources.md#src-008) | 익숙한 전문 용어는 유지할 수 있다. 모든 마케팅 표현·추상어를 금지하는 기준이 아니다. |
| 전문가를 위한 설명도 분명히 쓰며, 모호한 내부 용어 대신 실제로 하는 일을 구체적으로 표현한다. 필요한 전문 용어는 사용할 수 있다. | GOV.UK 「Use clear language」, 전문가·전문 용어·사용자 어휘 절. [SRC-084](sources.md#src-084) | 영어의 고정 대체어·어형·문장 길이를 한국어 정답으로 쓰지 않는다. |
| 문장을 추가하기 전에 인터페이스를 검토하고, 제목은 내용의 목적을 드러내며, 권리·의무 안내도 이해하기 쉽게 쓴다. | GOV.UK 「Writing for user interfaces」, 안내 추가 전 대안·제목·Legal content. [SRC-085](sources.md#src-085) | 법률 해석이나 원래 이용 조건 변경의 근거가 아니다. 한국어 표현 판단에는 한국어 자료를 함께 쓴다. |
| 내부 스펙을 보기 좋게 분류해도 개발자는 읽는 순서를 알지 못했다. 독자의 작업 순서와 컴포넌트 특성에 맞춰 문서를 구성했다. | 토스 디자인 시스템 가이드 개선 사례. [SRC-086](sources.md#src-086) | 해당 팀의 경험이며 모든 문서에 같은 구조를 강제하거나 효과를 일반화하지 않는다. |
| 사용자에게 표현의 뜻을 자신의 말로 설명하게 하고, 다음 화면의 예상과 읽은 뒤 할 일을 확인한다. 정책·법적 의미를 보존하며 수정한다. | GOV.UK 「What does this mean?」, 2~4·6·8절. [SRC-087](sources.md#src-087) | 실제 참여자 조사 방법이다. 에이전트의 해석을 독자의 관찰 결과로 취급하지 않는다. |

## 실행 절차에 연결하기

다음은 원문의 문장을 그대로 옮긴 규범이 아니라 이 스킬의 적용 절차다.

1. 문구를 읽는 사람과 여기서 답해야 할 질문을 정한다. 제품 사용자, 설치하려는 개발자, 내부 검토자가 같은 지식을 가진 것으로 보지 않는다.
2. 현재 안내만으로 알 수 있는 대상·행동·결과·조건을 적는다. 내부 분류나 기획 설명을 추가해야만 뜻이 드러나는지 확인한다.
3. 유지하는 문구에도 해당 사용처의 근거를 남긴다. 여러 종류의 문구에 같은 일반 사유를 반복하는 것으로 검토를 대신하지 않는다.
4. 수정안에도 같은 확인을 반복한다. 원문보다 내부 절차를 정확히 설명했다는 이유만으로 더 쉬워졌다고 판단하지 않는다. 이름이나 분류를 되풀이했을 뿐 필요한 대상·행동·적용 범위·조건이 분명해지지 않았다면 해결로 인정하지 않는다. 이는 SRC-043의 독자 질문·필요 정보 확인과 SRC-008의 구체적인 기능 전달을 수정안에 적용한 절차다. 모든 반복이나 법률 문구를 불필요하다고 판정하는 규칙은 아니다.

`KO-08`은 독자가 필요한 뜻을 구체적으로 알 수 있는 표현을 판단한다. `LT-05`에서는 표현 때문에 안내 의도가 흐려지는지 확인하고, UX 규칙은 필요한 정보와 제공 위치를 판단한다. 한쪽의 근거로 다른 쪽을 자동 통과시키지 않는다.

### 작업 안내 문서에 적용하기

README·설치 안내에서는 문단뿐 아니라 독자가 선택하고 실행하고 생성물을 수정하는 순서를 확인한다. 이는 SRC-086의 독자 작업 순서와 [안내 시점 근거](user-perspective.md)의 SRC-081·083을 문서에 적용한 절차다. 뒤의 제약이 앞선 선택에 영향을 주면 처음 필요한 위치를 찾는다. 모든 경고를 문서 맨 앞으로 옮기라는 규칙은 아니다.

SRC-043의 독자 질문·필요 정보와 SRC-008의 구체적인 기능 전달을 적용해 실행 예와 필수 조건, 보존 범위, 생성물과 실행 결과를 구별해서 읽는다. 실제 성립 조건은 제품 자료로 확인한다. 이 구분은 출처가 열거한 문장 유형이나 특정 제품의 정답 목록이 아니라 누락을 줄이기 위한 운영상 점검 항목이다. 이미 문맥으로 분명한 예시·전문 용어는 유지하며, 추가 설명의 필요성과 효과를 실제 독자 관찰 없이 확정하지 않는다.

권리·이용 조건은 정확한 대상과 조건을 확인해 설명한다. 권리를 가진 사람을 작성자로 자동 치환하지 않고, 법률 용어라는 이유로 어려운 문장을 그대로 두지도 않는다. `과업`, `흐름`, `권리자` 같은 단어를 금칙어로 등록하는 기준이 아니다.
