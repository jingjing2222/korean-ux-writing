# 제품의 설명과 사용자가 이해할 수 있는 맥락 구분하기

제품의 내부 동작을 아는 것만으로 사용자가 그 흐름을 이해할 수 있다고 판단할 수 없다. 아래 외부 자료는 사용자 과업, 사전 지식, 화면 단서, 안내 시점을 평가하는 근거다. 한국어 어휘·문장 판단은 별도 [한국어 근거](korean.md)와 연결한다.

## 확인한 근거

| 판단할 문제 | 원문에서 확인한 내용 | 출처 |
|---|---|---|
| 검토 과업이 정답을 알려주는가 | 목표와 상황을 제시하되 클릭 경로·화면 명칭으로 행동을 유도하지 않는다. | [SRC-076](sources.md#src-076) |
| 평가자의 해석을 사용자 이해로 취급하는가 | 질문에 해석·감정·요소의 정체를 넣으면 응답과 이후 행동이 달라질 수 있다. | [SRC-077](sources.md#src-077) |
| 사용자가 기억해야만 진행할 수 있는가 | 필요한 정보와 행동의 단서를 보이고 쉽게 접근할 수 있게 한다. | [SRC-078](sources.md#src-078) |
| 실제 사용자 테스트를 했는가 | 실제 또는 잠재 사용자의 과업 수행을 중립적으로 관찰하는 연구와 평가자의 추론은 다르다. | [SRC-079](sources.md#src-079) |
| 사용자의 지식을 개발자가 과대 가정하는가 | 인지적 워크스루는 사전 지식, 행동 발견, 기대 효과와 결과 이해를 단계별로 검토한다. 탐색 학습에 초점을 둔 전문가 평가다. | [SRC-080](sources.md#src-080) |
| 앞선 설명만으로 다음 단계를 이해한다고 가정하는가 | 토스는 화면 하나의 클릭보다 실제 탐색 경로를 추적하고, 단계별로 필요한 정보를 제공했다. | [SRC-081](sources.md#src-081) |
| 필요한 사전 맥락을 건너뛰는 진입 경로인가 | GOV.UK는 더 넓은 절차의 이해가 필요한 경우 진입점을 안내 흐름 안에 배치한다. | [SRC-082](sources.md#src-082) |
| 시스템이 편한 때 설명하는가 | NN/g는 사용자에게 필요한 때 안내하고, 상세 내용을 단계적으로 제공하며 재접근할 수 있게 하도록 한다. | [SRC-083](sources.md#src-083) |

## 이 스킬에 적용하는 방식

다음은 외부 원문을 그대로 옮긴 규범이 아니라, 위 근거와 사용자의 요구를 실행하기 위한 설계다.

1. **사실과 이용 맥락을 분리한다.** 코드·설계 문서·개발 세션은 실제 동작과 제약의 확인 자료다. 사용자에게 제공된 정보, 검증된 사전 지식, 과업의 근거를 따로 기록한다. 뒤 화면의 설명이나 다른 분기에서만 보이는 안내를 현재 사용자에게 소급하지 않는다.
2. **행동 전에 예상부터 남긴다.** 세션 이력이 없는 검토자에게 사용자 화면을 순서대로 제시할 수 있으면 그 방식을 쓴다. 이미 내부 사실을 안다면 독립 검토라고 하지 않는다. 실제 참여자 관찰 없이 사용자 발언·성공률·선호를 만들지 않는다.
3. **선행 맥락 누락은 흐름 문제로 다룬다.** 필요한 정보가 처음 요구되는 지점과 빠진 진입·안내 단계를 찾는다. 현재 문구에 설명을 붙이는 것으로 종결하지 않고 흐름 개선안을 남긴다. 이미 제공한 정보의 짧은 재확인과 애초에 제공하지 않은 맥락을 구분한다.
4. **해결 범위를 구분한다.** 표현 문제, 흐름 문제, 두 문제가 함께 있는 경우를 나눈다. 문구 수정만 했다면 해결하지 않은 흐름 문제를 그대로 보고한다.

모든 사용자를 초보자로 가정하거나 모든 기능에 온보딩을 추가하는 근거는 아니다. 전문 사용자의 실제 지식, 필요한 안내 시점, 재방문 경로를 확인한다. 개별 사례의 형식·수치나 전문가 점검 결과를 보편적인 사용자 행동으로 일반화하지 않는다.

실행 규칙은 `UX-12`(사용자에게 주어진 정보와 단계별 이해), `UX-13`(정보 제공의 시점과 흐름)에 연결했다. 규칙·기록 형식·검사기의 성공이 사용자 이해를 증명하지는 않는다.
