# 외부 근거 원문과 적용 범위

이 목록은 외부 문서의 확인한 내용을 요약한 증적이다. 레포 자체가 문구 품질의 원천이 되는 것은 아니다. `원문에서 확인한 내용`과 `운영상 적용 해석`을 구분하며, 후자는 외부 원문이 직접 명시한 새 규칙으로 취급하지 않는다. 전체 문서의 복제나 모든 사례의 일괄 채택을 포함하지 않는다.

검증 상태의 의미와 책임 구분은 [증적 안내](README.md)를 따른다. [UX 역할별 연결](ux.md)과 [한국어 윤문 연결](korean.md)은 이 목록의 출처 ID로 돌아온다.

## SRC-001 · 토스의 8가지 라이팅 원칙들

- 원문: [토스의 8가지 라이팅 원칙들](https://toss.tech/article/21022)
- 발행 주체·자료 성격: 토스 · 제품 원칙
- 확인 위치: Predictable hint, Weed cutting, Remove empty sentences, Easy to speak, Suggest over force의 설명과 사례
- 원문에서 확인한 내용: 다음 행동을 예측하도록 표현하고 의미 없는 단어·중복 문장을 줄인다. 말로 읽기 쉬운 표현과 짧은 호흡을 권하며 가능한 경우 한 문장에 하나의 메시지를 담도록 한다.
- 적용 조건·범위: 사용자에게 행동과 결과를 전달하는 제품 문구. 토스의 원칙과 사례가 제시된 맥락.
- 예외·한계: 원문은 사례만으로 문장의 정오를 단정할 수 없다고 설명한다. 토스 말투와 모든 표현 선택을 범용 규범으로 강제하지 않는다.
- 운영상 적용 해석: 행동 예고가 부족하거나 의미 없는 반복이 있는지 찾는 근거로 사용한다. 제품별 보이스톤은 별도로 확인한다.
- 확인 상태: `passage-checked` · 2026-10-21. 조사 과정에서 locator에 적은 본문 구절과 사례를 확인했다. 문서 전체의 검증·독립 실험 결과·인간 승인 상태를 의미하지 않는다.

## SRC-002 · 좋은 에러 메시지를 만드는 6가지 원칙

- 원문: [좋은 에러 메시지를 만드는 6가지 원칙](https://toss.tech/article/how-to-write-error-message)
- 발행 주체·자료 성격: 토스 · 작성 지침
- 확인 위치: 도입의 상황·이유·해결책, 사용자 이해와 해결 행동 설명, 아이디·비밀번호의 보안 예외
- 원문에서 확인한 내용: 오류의 상황과 이해에 필요한 이유, 가능한 해결 행동을 사용자 관점에서 안내하되 보안상 상세 원인을 공개하면 안 되는 예외를 고려한다.
- 적용 조건·범위: 오류 발생과 복구를 안내하는 메시지. 원인·복구 동작이 확인된 상황.
- 예외·한계: 알려지지 않은 원인을 추정하거나 존재하지 않는 복구 기능을 안내하는 근거가 아니다. 보안 예외가 있다.
- 운영상 적용 해석: 코드와 실제 화면에서 오류 조건·복구 동작을 확인한 뒤 필요한 정보가 메시지에 있는지 검토한다.
