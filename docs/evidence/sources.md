# 외부 근거 원문과 적용 범위

이 목록은 외부 문서의 확인한 내용을 요약한 증적이다. 레포 자체가 문구 품질의 원천이 되는 것은 아니다. `원문에서 확인한 내용`과 `운영상 적용 해석`을 구분하며, 후자는 외부 원문이 직접 명시한 새 규칙으로 취급하지 않는다. 전체 문서의 복제나 모든 사례의 일괄 채택을 포함하지 않는다.

검증 상태의 의미와 책임 구분은 [증적 안내](README.md)를 따른다. [UX 역할별 연결](ux.md)과 [한국어 윤문 연결](korean.md)은 이 목록의 출처 ID로 돌아온다.

## SRC-001 · 토스의 8가지 라이팅 원칙들

- 원문: [토스의 8가지 라이팅 원칙들](https://toss.tech/article/21022)
- 발행 주체·자료 성격: 토스 · 제품 원칙
- 확인 위치: Predictable hint, Weed cutting, Remove empty sentences, Easy to speak, Suggest over force의 설명과 사례
- 원문에서 확인한 내용: 다음 행동을 예측하도록 표현하고 의미 없는 단어·중복 문장을 줄인다. 말로 읽기 쉬운 표현과 짧은 호흡을 권하며 가능한 경우 한 문장에 하나의 메시지를 담도록 한다.
- 적용 조건·범위: 사용자에게 행동과 결과를 전달하는 제품 문구. 토스의 원칙과 사례가 제시된 맥락.
- 예외·한계: 원문은 사례만으로 문장의 정오를 단정할 수 없다고 설명한다. 토스 말투와 모든 표현 선택을 범용 규범으로 강제하지 않는다.
- 운영상 적용 해석: 행동 예고가 부족하거나 의미 없는 반복이 있는지 찾는 근거로 사용한다. 제품별 보이스톤은 별도로 확인한다.
- 확인 상태: `passage-checked` · 2026-10-21. 조사 과정에서 locator에 적은 본문 구절과 사례를 확인했다. 문서 전체의 검증·독립 실험 결과·인간 승인 상태를 의미하지 않는다.

## SRC-002 · 좋은 에러 메시지를 만드는 6가지 원칙

- 원문: [좋은 에러 메시지를 만드는 6가지 원칙](https://toss.tech/article/how-to-write-error-message)
- 발행 주체·자료 성격: 토스 · 작성 지침
- 확인 위치: 도입의 상황·이유·해결책, 사용자 이해와 해결 행동 설명, 아이디·비밀번호의 보안 예외
- 원문에서 확인한 내용: 오류의 상황과 이해에 필요한 이유, 가능한 해결 행동을 사용자 관점에서 안내하되 보안상 상세 원인을 공개하면 안 되는 예외를 고려한다.
- 적용 조건·범위: 오류 발생과 복구를 안내하는 메시지. 원인·복구 동작이 확인된 상황.
- 예외·한계: 알려지지 않은 원인을 추정하거나 존재하지 않는 복구 기능을 안내하는 근거가 아니다. 보안 예외가 있다.
- 운영상 적용 해석: 코드와 실제 화면에서 오류 조건·복구 동작을 확인한 뒤 필요한 정보가 메시지에 있는지 검토한다.

## SRC-008 · Designing Words — 삼성 UX Writing 가이드

- 원문: [Designing Words — 삼성 UX Writing 가이드](https://design.samsung.com/kr/contents/ux-writing/)
- 발행 주체·자료 성격: 삼성 MX UX Team · 제품 원칙
- 확인 위치: 사용자를 위한 글 디자인, 불리한 상황도 솔직하게 알리기, 이론서처럼 쓰지 않기, User-Friendly 설명; 사용자를 위한 글 디자인: 사용하는 사람의 입장에서 용어를 고르는 질문; 스마트한 라이프를 위한 유용한 기능 사례와 바로 뒤 두 단락; 이론서를 쓰는 게 아니다의 용어 예외.
- 원문에서 확인한 내용: 공허한 홍보 표현보다 사용자가 필요한 정보를 전달하고 불리한 상황도 정확하게 알린다. 사용자 친화성을 무조건 친근한 말투와 동일시하지 않는다. 어떤 기능에도 적용될 수 있는 추상적인 소개는 실제 기능을 전달하지 못한다. 기능 안내는 사용에 도움이 되어야 하며, 용어는 제공자보다 사용자의 관점에서 선택한다.
- 적용 조건·범위: 삼성 제품의 사용자 안내를 설명하는 UX Writing 원칙.
- 예외·한계: 삼성의 브랜드 표현을 그대로 복제할 근거가 아니며 모든 메시지를 긍정형·친근한 말투로 바꾸지 않는다.
- 운영상 적용 해석: 아래 비교 질문은 원문 사례를 일반 검토에 적용한 프로젝트 절차다. 제품명과 내부 분류명을 다른 것으로 바꿔도 그대로 맞는 문장인가? 그렇다면 이 독자에게 필요한 구체적 기능이나 결과를 누락한 것은 아닌가?
- 확인 상태: `passage-checked` · 2026-10-21. 조사 과정에서 locator에 적은 본문 구절과 사례를 확인했다. 문서 전체의 검증·독립 실험 결과·인간 승인 상태를 의미하지 않는다.

## SRC-086 · 제품이 커지면 디자인 시스템 가이드는 어떻게 개선돼야 할까?

- 원문: [제품이 커지면 디자인 시스템 가이드는 어떻게 개선돼야 할까?](https://toss.tech/article/toss-design-system-guide)
- 발행 주체·자료 성격: 토스 · 황희영, Platform Designer · 제품 문서 개선 사례
- 확인 위치: 가이드 읽는 방향성 정하기; 큰 구조부터 자세한 요소로; 수십개의 컴포넌트 가이드에 적용하기.
- 원문에서 확인한 내용: 작성자가 스펙을 보기 좋게 묶어 놓아도 개발자는 읽는 순서와 구현 구조를 파악하지 못했다. 독자의 작업 순서와 컴포넌트 특성에 맞게 문서를 구성하고 불필요한 정보를 생략한 사례를 설명한다.
- 적용 조건·범위: 디자이너와 개발자가 사용하는 디자인 시스템 컴포넌트 가이드의 구성 개선 사례.
- 예외·한계: 해당 팀의 경험 사례이며 보편적인 효과 크기나 실험 결과가 아니다. 항상 위에서 아래로 읽게 하거나 모든 문서를 같은 템플릿에 맞추라는 규칙으로 확대하지 않는다. 개발자 독자라 해도 해당 제품의 내부 분류와 문서 구조를 자동으로 이해한다고 보지 않는 근거로 쓴다.
- 운영상 적용 해석: 내부 분류를 독자의 다음 행동과 연결하라는 적용은 이 사례를 바탕으로 한 프로젝트의 검토 절차다. 작성자의 검토 항목을 나열하는 대신, 읽는 사람이 어떤 순서로 무엇을 판단하거나 실행할 수 있는지 드러나는가?
- 확인 상태: `passage-checked` · 2026-10-21. 공식 페이지 본문을 웹 도구로 읽고, 재요청이 타임아웃된 뒤 같은 공식 URL을 urllib로 직접 내려받아 해당 절을 다시 확인했다. 기록한 부분의 확인이며 문서 전체 검증이나 독자 이해의 관찰 결과가 아니다.
