# Working on this skill

Read `docs/evidence/README.md` before changing writing rules. UX rules govern what a funnel must communicate; Korean rules govern how to express that meaning. Product code establishes facts, not writing standards.

Never promote an invented preference or another agent skill into a writing rule. Preserve source scope, exceptions, and verification limits. Keep the full source evidence in `docs/evidence/`, outside `skills/`.

Assume a product written in Korean with no English source. Compare its Korean copy directly with the task and consequences established from product context; do not reconstruct an imagined English original. Read the entire affected funnel before editing product copy. Diagnose intent and Korean word choice before rewriting; grammatical pattern checks alone are insufficient. Track entry points, earlier promises, branches, exits, recovery, and later consequences. A component in isolation is not sufficient context. Record the current Korean reading against the intended meaning at every usage site. Split inventory meanings before diagnosis when one source key serves different tasks; polish only after resolving the mismatch.

Keep the two READMEs concise and equivalent. Run the repository validator and behavioral tests before publishing changes. Do not add local work reports, private checklists, credentials, or workstation paths.
